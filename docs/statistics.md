# 输入统计

冰雪拼音的五个方案（冰雪四拼、冰雪三拼、冰雪一拼、冰雪键道、冰雪清韵）记录用户的输入过程，输入 `otj` 等命令即可查看词数、速度、码长等统计。给用户看的用法和各量的一行说明在 `lua/snow/statistics.lua` 的文件头注释里；本文记录统计口径和设计取舍，改动统计逻辑前先读。

全文分三部分：

1. **事件模型**：输入法看到的是什么，统计所说的「键」和「上屏」各指什么；
2. **统计量**：在这两类事件之上定义要计算的量；
3. **实现**：这些定义在 Lua 里怎么落地。

## 一、事件模型

统计把输入过程看成两条交织的事件流：用户敲下的**键**，和输入法向应用发出的**上屏**。统计的核心是把每个键归到某一次上屏上，然后按上屏汇总。

### 键

本文所说的「键」不是系统层面的一个按键事件，而是**用户意图上的一次击键**，一个逻辑符号：

- **普通按键**：按下算一个键，松开不算。
- **组合键**：修饰键（Shift、Ctrl、Alt、Super 等）和别的键一起按时，整组算一个键，算在那个非修饰键上。单独按下又松开的修饰键（例如切换临时西文的 Shift）不算。
- **并击**（冰雪一拼）：从一组并击的第一个键按下，到所有键都松开，整组算一个键，时刻取最后一个键松开的那一刻。

此外，不是所有的键都计入统计，只有属于**中文输入**的键才算：

- 全局西文和临时西文下的键都不算。
- 有编码（输入框非空）时，所有键都算：字母、退格、方向键、Escape、空格、选重键、组合键等。
- 没有编码时，只算会开始一段输入或者会直接上屏的可见字符（ASCII 的 `!` 到 `~`），而且不能带 Ctrl、Alt、Super。快捷键属于应用，不算；单独输入的空格、回车、Tab 等空白符只是排版，也不算。

把计入的键按时间顺序编号为 $1, 2, \dots$，第 $i$ 个键 $k_i$ 有两个属性。

**时刻** $t_i$，单位为毫秒。由此定义这个键占用的**时长**

$$
\delta_i=\begin{cases}t_i-t_{i-1} & t_i-t_{i-1}<\tau\\ 0 & t_i-t_{i-1}\ge\tau\end{cases},\qquad \tau=5000
$$

间隔达到 $\tau$ 视为停顿，停顿后的第一个键时长为 0。统计衡量的是打字本身，不是想内容的时间。

**编辑量** $e_i\in\{-1,0,+1\}$，表示这个键对输入净贡献了几个逻辑符号：

- 退格为 $-1$；
- 无效并击（组合不对应任何编码、被方案整个丢掉）为 $0$，串击方案无此情况；
- 其他键为 $+1$。

### 上屏

上屏是输入法向应用发出的一段文字。按来源分三类：

1. **经过输入框的上屏**：选词、空格上屏首选、顶功顶屏、回车上屏编码、标点等。这类上屏发生时输入框里有编码，上屏后编码被清空或部分清空。
2. **直接放行的字符**：没有编码时按下的可见字符（数字、标点等），输入法不处理，原样交给应用。统计把它当成一次上屏，文字就是这个字符。
3. **绕过输入框的上屏**：以词定字、略码等由方案自己的 Lua 逻辑直接发出的文字。

第 $j$ 次上屏的文字记为 $c_j$，它的 Unicode 字符数记为 $l_j$。$l_j=0$ 的上屏不计。

### 忽略规则

以下情况下，某些键或上屏不会计入统计：

- **临时西文下的上屏**：临时西文会把已经打的中文编码换成对应的字母一起上屏。这次上屏不记，进入临时西文之前打的中文编码也不算，之前累计的键全部丢掉。如果没有改动就切回中文，编码会还原，之前的键保留，接着累计。
- **统计命令本身**，以及方案配置里列出要屏蔽的输入（整个输入与某个正则完全匹配）。这次上屏不记，归给它的键照样取走丢掉。屏蔽只对第 1 类上屏有效：另两类上屏时输入框要么是空的，要么内容取决于调用方，按输入判断没有意义。
- 输入框从有编码变成没有编码，而中间没有任何上屏，就认为用户放弃了这段输入：Escape、退格删光、用其他组件清空输入框都是。这时**所有待结算的键都丢掉**，包括清空编码的那个键。

除忽略规则定义的以外，其他所有键都需要归到一次上屏，且每次上屏也都需要分到至少一个键。下面是决定如何归属的问题。

### 键归到哪次上屏

键和上屏交替发生。理想情况下的口径是「两次上屏之间的键属于后一次上屏」，所以选重键、上屏键都算在这次上屏上：冰雪四拼 `s_` 输入「我」是 2 个键。

顶功打破了这个口径：触发顶屏的键在时间上先于上屏，但它是**下一个词的首码**，而非属于这一个词。例如冰雪四拼输入 `bis_` 先后上屏「比」「我」，虽然上屏「比」是在打出 `s` 之后，但分配按键时应该是两个和两个键，而不是三个和一个。又例如四二顶类方案输入 `abcd` 时上屏 `ab` 对应的词，这要求我们需要精准地把前两个键对应到这次上屏。

所以每次上屏 $j$ 声明一个**移交量** $h_j\ge 0$，单位是编辑量：待结算的键里，末尾编辑量之和达到 $h_j$ 的那一段留给下一次上屏，其余的键归这次上屏。

形式化地，设上屏 $j$ 发生时待结算的键依次为 $k_1,\dots,k_p$，取最大的 $u$ 使得

$$
\sum_{i=u+1}^{p}e_i\ge h_j
$$

（不存在时取 $u=0$），则归这次上屏的键为 $s_j=\{k_1,\dots,k_u\}$，$k_{u+1},\dots,k_p$ 留下。$h_j=0$ 时 $u=p$，全部结算。

各类上屏的移交量：

| 上屏 | $h_j$ |
| --- | --- |
| 顶功且推回 $r$ 个键 | $r+1$ |
| 略码先上屏的原词 | $1$（略码键算作重复出来的部分的编码） |
| 其他 | $0$ |

按编辑量而不是按键数往回数，是为了让推回的编码中途改过也能分对：`abcx⌫d` 之后按 `e` 顶屏，推回 `cd`（$r=2$，$h_j=3$），从末尾往回累加 `e` `d` `⌫` `x` `c` 的编辑量，到 `c` 时达到 3，所以 `cx⌫de` 留给下一个词，`ab` 记 2 个键。只要每个 $e_i=+1$ 的键都往输入框里加了一个字符、每个退格都删了一个字符，分界就是精确的：从末尾累加到 $h_j$ 的位置，正是输入框长度最后一次等于「顶屏前的长度减 $r$」的时刻，此后前面的编码再没被动过。

只有在顶屏真正发生、而触发它的键还没有被继续处理之前，才需要移交。键被继续处理之后引起的上屏（这个键作为标点被上屏、满足自动上屏条件、作为空格选词）不移交，这时这个键确实属于这次上屏。

略码先上屏原词、再上屏重复出来的部分，统计记成「原词」和「重复部分」两次，重复部分不管接在词前还是词后都合成一次。

## 二、统计量

### 每次上屏的量

对计入统计的第 $j$ 次上屏，由归给它的键集合 $s_j$ 定义：

$$
n_j=|s_j|,\qquad m_j=\sum_{i\in s_j}e_i,\qquad d_j=\sum_{i\in s_j}\delta_i
$$

分别是**按键数**、**有效按键数**和**时长**，再加上第一部分定义的字数 $l_j$。

有效按键数近似于「不打错时需要的按键数」：有编码时每按一次退格，按键数加 1、有效按键数减 1，所以两者的差增加 2。

按键归属正确时每次上屏至少有一个有效按键，即 $m_j\ge 1$。$m_j\le 0$ 说明归属出了偏差（见第三部分的「已知局限」），这次上屏**整次丢掉**，清除键集合。

### 每个单元的量

定义单元为「日期 × 方案 × 安装」的三元组，每次上屏属于它发生时所在的方案、本地日期和安装（设备）。方案之间码长不可比，所以按方案分开；设备之间速度不可比（电脑和手机），所以按安装分开。

一个单元内，对其中所有计入的上屏 $j$ 求和，得到总按键数 $n$、总时长 $d$：
$$
n=\sum_j n_j,\qquad d=\sum_j d_j
$$
以及词长分布 $L(x)$ 和码长分布 $M(x)$，它们是定义域 $\mathbb Z^+$、值域 $\mathbb N$ 的函数：
$$
L(x)=\bigl|\{j: l_j=x\}\bigr|,\qquad M(x)=\bigl|\{j: m_j=x\}\bigr|\quad(x\in\mathbb Z^+)
$$

词数 $w$、字数 $c$、有效按键数 $m$ 都由分布算出：

$$
w=\sum_x L(x)=\sum_x M(x),\qquad c=\sum_x x\,L(x),\qquad m=\sum_x x\,M(x)
$$

由定义直接得到两个**不变式**，改口径后可以用它们检查数据：

$$
\sum_x L(x)=\sum_x M(x),\qquad \sum_x x\,M(x)\le n
$$

前者因为它们都等于词数 $w$，后者因为 $m_j\le n_j$。

### 极速窗口

在同一个会话（从启用方案到切走或重启输入法）内，把计入的上屏按顺序分成若干段连续的组：每组从上一组结束后开始累加，累加到时长达到 $6\times10^4$ ms（一分钟）就结束。对每个结束的组 $g$，记它的字数和时长

$$
c_g=\sum_{j\in g}l_j,\qquad d_g=\sum_{j\in g}d_j\ge 6\times10^4
$$

一个单元的**极速窗口** $(c^\ast,d^\ast)$ 是单元内 $c_g/d_g$ 最大的那一组。会话末尾不满一分钟的组不参与。

窗口不滑动，所以它不是严格的「最快一分钟」，而是「某段至少一分钟的输入的平均速度」的最大值。

### 时段汇总

报告按时段汇总若干单元：今日、本周（从周一算起）、本月、本年、累计，各取当前方案下日期落在时段内的单元，安装取本机、全部或逐个列出。

- $n$、$d$、$L(x)$、$M(x)$ 直接相加；
- 极速窗口取所有单元中 $c^\ast/d^\ast$ 最大的那个。

### 报告中的量

对汇总后的数据，时长 $d$ 以毫秒计，另外定义 $d_{\rm S}=d/1000$ 为秒数，$d_{\rm M}=d_{\rm S}/60$ 为分钟数：

| 量 | 公式 | 单位 |
| --- | --- | --- |
| 词 | $w$ | |
| 字 | $c$ | |
| 用时 | $d_{\rm M}$ | 分 |
| 键 | $n$ | |
| 有效键 | $m$ | |
| 键准 | $m/n$ | |
| 均速 | $c/d_{\rm M}$ | 字/分 |
| 极速 | $c^\ast/d^\ast_{\rm M}$ | 字/分 |
| 击键 | $n/d_{\rm S}$ | 键/秒 |
| 码长 | $n/c$ | |
| 理论码长 | $m/c$ | |
| 平均词长 | $c/w$ | |
| 多字词占比 | $1-L(1)/c$ | |
| 词长分布 | 各档 $L(x)/w$ | |
| 码长分布 | 各档 $M(x)/w$ | |

在报告时，极速会和均速取最大值：库里的窗口不一定代表时段内最快的一段。会话末尾不满一分钟的组不结算，快的那段可能正好落在里面；一天的输入不满一分钟时，一个窗口都没有。只看窗口的话，极速可能低于均速。而整个时段只要 $d\ge 6\times10^4$，本身就是「一段至少一分钟的输入」，它的平均速度按定义也是候选。所以取两者的最大值，任何时段都有均速不超过极速。$d<6\times10^4$ 时不存在满一分钟的段，不显示极速。这个最大值只在显示时取，库里仍只存原始窗口。

## 三、实现

### 组件

统计由 `lua/snow/statistics.lua` 的两个组件实现：

- `lua_processor@*snow.statistics*processor` 排在 processors **第一位**，只观察按键，除了并击的最后一次松开（见「并击」）都返回 `kNoop`。它把每个计入的键追加到 `env.steps`，在每次上屏时结算写库。排第一是因为 `ascii_composer` 会吃掉临时西文下的按键（要靠它们判断临时西文是否上屏了），`shape_processor`、`select_character` 等也会 `kAccepted` 掉按键，排在它们后面就看不到这些键了。
- `lua_translator@*snow.statistics*translator` 紧跟在 `datetime` 后面，处理统计命令。如果排在 `calculator` 后面，首选会被计算器回显的 `tj` 抢走。

命令为前缀加 `tj`，前缀取自 `lua/input`，和 datetime、number、calculator 共用：

- `tj` 前加 `r` / `z` / `y` / `n` / `q` 只看今日、本周、本月、本年、累计中的一个时段，如 `ortj`；
- `tj` 后加 `q` 合并所有安装，加 `s` 逐个列出安装，如 `otjq`、`oqtjs`。

多数方案的前缀是 `o`。冰雪一拼的 `o` 会被 `combo_popping` 吞掉，所以改用 `i`，和符号一致（`itj` 等没有和符号码重复）；命令由 `chord_composer/algebra` 里的右手并击 `jkl` / `jkl;` / `uio` 打出，结果加方括号，以免被 `output_format` 当成非法音节删掉。冰雪清韵的 `o` 是普通编码，所以用两个着重号 ``` `` ```。单个 `` ` `` 在冰雪清韵里引导拼音、笔画反查和重复上屏，对应的 recognizer 规则（`` ^`[a-z]*'?$ ``、`` ^`$ ``）都匹配不到第二个字符是 `` ` `` 的输入，所以 `` ^``.*$ `` 和它们互不重叠。前缀可以是多个字符，各 lua 翻译器要按 `#env.prompt` 比较和截取，不能写 `input:sub(1, 1)`。

### 存储与同步

- 只有一个库 `snow_statistics.userdb`，所有方案、所有安装共用，通过 `snow.get_db` / `release_db` 做引用计数。processor 和 translator 各持有一次引用。
- 键为 `<schema_id> <YYYYMMDD> <installation_id> \t<字段>`，值为 `c=<计数> d=0 t=1`。这是用户词典快照的格式：librime 同步时把所有 `.userdb` 当用户词典处理，格式不对的键会被丢掉，格式不对的值会被改写成 0（见 CLAUDE.md 的「lua 的三处坑」）。
- 每个单元存这些字段，和第二部分的符号对应如下：

  | 字段 | 符号 |
  | --- | --- |
  | `keys` | $n$ |
  | `duration` | $d$ |
  | `word<x>` | $L(x)$ |
  | `code<x>` | $M(x)$ |
  | `window_chars`、`window_duration` | $c^\ast$、$d^\ast$ |

  只存原始计数，比率在显示时再算。计数可以相加、合并、同步；周、月、年在查询时把各天加起来，库里没有无限增长的数组。一天的 `duration` 最多约 $8.64\times10^7$ ms，不会超出 `c=` 解析用的 int。窗口存字数和时长两个整数而不存速度，是因为 `c=` 只能存整数。
- 日期取结算（上屏）那一刻的本地日期，安装取 `rime_api.get_user_id()`，即 `installation.yaml` 的 `installation_id`。

多设备同步靠**只增不减**：每个安装只写带自己 `installation_id` 的键，`UserDbMerger` 对同一个键取 `c` 的最大值，结果正好是该安装的最新值；重复同步结果不变（用 `rime_dict_manager -b` / `-r` 实测过往返）。为了保证单调：

- $m_j\le 0$ 的上屏整次丢掉，不写负增量；
- 极速窗口的两个字段只在速度更高时一起覆盖。它们不一定各自递增（速度更高的窗口可能字数更少），合并时各取最大值，结果可能拼自两个窗口。窗口时长都在一分钟上下，偏差很小，接受；
- 移交量必须在上屏前由触发上屏的组件声明，不能事后修正（见第一部分）。

两台设备的 `installation_id` 相同时，它们的数据会按最大值互相覆盖，这是这种方案的前提。

### 识别键（`processor.func`）

每个按键事件依次经过：

1. `snow.redispatching` 为真时跳过：popping 用 `engine:process_key()` 把同一个键重投到链顶，第一次已经记过了。`env.finishing` 为真时也跳过，这是并击的合成键（见「并击」）。
2. **放弃检测**。processor 排在第一位，所以事件开始时看到的就是上一个事件处理完的状态。如果 `env.composing`（上一个事件开始时有编码）为真、现在没有编码、`env.committed`（期间有过上屏）为假，就清空 `env.steps`，然后把这两个字段换成当前的值。

   检测不针对具体的键，而是比较前后两个事件，所以不用在按下时判断这个键会不会清空编码：Escape 在有已确认的段时只清最后一段（`ClearPreviousSegment`），key_binder 还会把 `Control+g`、`Control+bracketleft` 转成 Escape。清空编码的那个键最晚到它自己的松开事件就会被结算掉。除了第 1 步跳过的合成键，所有事件（含松开、`ascii_mode` 下的键）都要做这一步。
3. `ascii_mode` 为真时跳过，包括全局西文和临时西文。
4. 并击方案先按「并击」一节处理并击键。
5. 松开事件和修饰键（`0xffe1`–`0xffee`）本身跳过。修饰键和别的键一起按时，那个键的事件带着修饰键状态，照常计入，所以整组只算一个。
6. 没有编码时，带 Ctrl/Alt/Super 的键、以及 `0x21`–`0x7e` 以外的键跳过。
7. 其余的键调用 `step` 记入 `env.steps`：编辑量为退格 −1、其他 +1，时长按 $\tau$ 截断，时刻取自 `rime_api.get_time_ms()`（单调时钟，不是墙上时间，只能用来算间隔）。

临时西文下的上屏有两条路径，都要清掉 `env.steps`：

- 本机改过的 librime（`~/Public/librime`）里，空格、回车、改动过西文后切回中文等都由 ascii_composer 调用 `engine:CommitText`，不经过 `commit_notifier`，也就是编码没了而没有上屏，第 2 步正好清空；
- 原版 librime（mira 用的是 Homebrew 的 1.17）里，回车走 express_editor 的 `context:commit()`，这时 `ascii_mode` 还开着，所以 `commit_notifier` 的回调里遇到 `ascii_mode` 也清空、不记。

### 并击（冰雪一拼）

方案配置里有 `chord_composer/alphabet` 时，processor 按旧版 `ChordComposer`（`librime/src/rime/gear/chord_composer.cc`）的规则跟踪并击：

- chord_composer 吃掉并击键的按下和松开。所有键都松开时，它把并击序列化、过 `algebra` 和 `output_format`，再把结果**逐个字符用 `ProcessSyntheticKey` 从链顶重投**（`bay`、`iduh `、`od ` 之类），没人处理的合成键由它直接 `CommitText`。合成键在 Lua 里和真实按键一样，都是字母的按下事件，没有标志可区分。
- processor 用 `env.held` 镜像 chord_composer 的 `pressed_keys`：不在 `ascii_mode` 时，按下 alphabet 里的键（无修饰键）只记进 `held`，不计数；非并击键或带修饰键的事件（按下、松开都算）清空 `held`，这和 C++ 里 `state_.Clear()` 的条件一致，键本身照普通按键处理。
- 让 `held` 变空的那次松开，就是 chord_composer 要 FinishChord 的时刻。processor 先记一个键，然后置 `env.finishing`，**自己调用 `engine:process_key()` 把这次松开交给后面的处理器**，返回后清掉 `finishing` 并返回 `kAccepted`。嵌套调用期间到达的事件都是合成键，一律跳过，只数一下按下事件的个数存进 `env.output`；`process_key` 是同步的，所以界限是精确的，不依赖计时。这个键必须**在重投之前**记下，因为重投中途就会上屏。
- `env.output` 为 0（`output_format` 把组合 erase 掉了）的并击照样计入按键，但编辑量改为 0。
- 空格也是并击键。没有编码时单按空格，chord_composer 合成的空格没人处理，由 `unhandled_key_notifier` 看到。这时回调置 `env.blank`，重投返回后把这组并击从 `env.steps` 里删掉，和非并击方案一样整个不记。删之前要确认它仍是最后一个：合成按键里如果先有别的上屏，它已经被结算走了。
- 时长取相邻两次结算并击（以及普通按键）之间的间隔。
- 没处理 `use_shift` 等选项（开了之后要像 C++ 那样换算到基础层），冰雪一拼没有开。

### 捕获上屏

三类上屏各有一条捕获路径：

| 来源 | 捕获方式 | 记作的上屏文字 |
| --- | --- | --- |
| 经过输入框：`context:commit()` | `commit_notifier` | `get_commit_text()` |
| 直接放行的字符，以及 chord_composer 因为没人处理而直接上屏的合成键 | `unhandled_key_notifier` | 这个字符 |
| 绕过输入框：`snow.commit_text` | `property_update_notifier`，属性名 `commit_text` | 属性值，即 `counted` 参数，默认为上屏的文字 |

- `engine:commit_text` 不触发 `commit_notifier`。**以后新写的直接上屏一律调用 `snow.commit_text`**，否则这次上屏的字数会漏记，它的按键也会被算进下一次上屏。
- 第一部分说的合并多次上屏，靠 `counted` 参数实现。略码重复出来的部分不管接在词前还是词后，词前的部分上屏时 `counted` 传空串不记，词后的部分上屏时 `counted` 传两部分之和；词本身用移交量 1 把略码键转给重复出来的部分。例如 `wgA` 记成「这个」2 码、重复的「这个」1 码。
- `unhandled_key_notifier` 对 `kRejected` 的键也会触发，所以回调里要排除 `ascii_mode`；还要排除 `snow.redispatching`，因为顶屏后重投、最终没人处理的键（比如空格）并没有到达应用。空格在这里也被排除，并击时顺便置 `env.blank`。
- 屏蔽只在 `commit_notifier` 的回调里做：`context.input` 是统计命令（和翻译器共用 `parse_command`，不用另配），或者与方案 `statistics/exclude` 列表里任一个正则**完全匹配**（`regex_match`）时，按移交量用 `take` 从 `env.steps` 里取出这次的键后丢掉，顶屏键仍留给下一个词。
- `commit_notifier` 和 `property_update_notifier` 的回调都置 `env.committed`，供放弃检测使用。

### 移交量（`snow.handover`）

移交量 $h_j$ 由触发上屏的组件在上屏前写进 `snow.handover`，上屏后置回 `nil`，统计在 `commit_notifier` 回调里读取：

- `popping.lua` 按规则顶屏时设为 `1 + (input:len() - rule.prefix)`（没有 `rule.prefix` 时为 1）。非缓冲模式下 popping 开着 `_auto_commit`，`confirm_current_selection()` 这一步就会上屏，所以 **必须在 confirm 之前设置**。第一版把它设在 `commit()` 前面，结果完全没有生效。重投之后的上屏（`auto_select_pattern` 触发的自动上屏等）不设置。
- `combo_popping.lua` 是在下一组并击的第一个合成字母上顶屏的，这时那组并击已经记进 `env.steps`，所以它的两处上屏都设为 1。
- `abbreviation.lua` 上屏原词时设为 1。

### 结算（`take`、`record`）

- `take(env, handover)` 从 `env.steps` 末尾往回累加 `effective`，直到达到 `handover`，前面的部分作为 $s_j$ 返回，后面的部分留在 `env.steps` 里。
- `record(env, text, handover)` 计算 $l_j$；$l_j=0$ 或库没打开时直接返回。否则调用 `take`，算出 $n_j$、$m_j$、$d_j$；$m_j\le 0$ 时整次丢掉，否则给当天的 `keys`、`duration`、`word<l_j>`、`code<m_j>` 加上增量。
- 极速窗口累加在 `env.window_chars`、`env.window_duration` 上，满一分钟时和库里当天的窗口比速度，更快才覆盖，然后清零。这两个字段只存在于 processor 实例上，所以窗口不跨会话。

### 报告（`translator.func`）

`collect` 按时段的日期前缀查出当前方案的记录，先按「方案 日期 安装」分组（极速窗口的两个字段要成对比较），再用 `merge` 合并：其余字段相加，窗口取速度更高的那个。`summarize` 从 `word<x>`、`code<x>` 算出 $w$、$c$、$m$ 和合并了长尾的分布，只认正整数档位，所以 `word0`、`code0` 这类异常值会被丢掉。

每个时段一个候选，文字按行排：

1. 📊 加日期范围加「统计数据」：今日「2026 年 10 月 10 日」，本周「2026 年 41 周」（ISO 8601 周数，年和周数都按本周的周四算，所以 1 月初可能显示为上一年的 52 或 53 周；不用 `os.date` 的 `%G`、`%V`，Windows 上的 Lua 不支持），本月「2026 年 10 月」，本年「2026 年」，累计「截至 2026 年 10 月 10 日累计」；
2. ⌨️ 加「方案：」接方案名和 id；
3. 💻 加「平台：」接 `distribution_code_name` 加版本（fcitx5-rime 的 `distribution_name` 只是 Rime，所以不用它）。`tjq` 改为「设备：全部」，`tjs` 改为「设备：<installation_id>」，本机再加「（本机）」——其他设备的平台库里没有记；
4. 分割线（14 个 `─`）；
5. 正文：词、字、用时；键、有效键、键准；均速、极速、击键；码长、理论码长；平均词长、多字词占比；分割线；词长分布；码长分布。时长不满 60 秒时省略极速。没有上屏时正文只有前三行。所有比值都经 `ratio` 计算，分母为 0 时记为 0；分布的各档用顿号隔开，四舍五入为 0% 的档不显示，长度用 `number.lua` 的 `chinese` 写成中文数字；
6. 分割线；
7. 署名「❄️ 冰雪统计 v0.3.11」，版本号取自 `snow.version`；
8. 「💬 冰雪拼音 QQ 群 1014366669」。

候选只显示 📊 加时段，即第一行去掉「统计数据」（`tjs` 另在注释里显示设备），全文记在 `env.reports` 里，键为候选文字加 `\t` 加注释，上屏时才换上。换的办法是在 `commit_notifier` 上以分组 0 连接一个回调：boost.signals2 先调用分组的回调，再调用未分组的，而引擎自己的 `OnCommit` 是未分组的，它随后用 `Composition::GetCommitText()` 按选中候选的 `text()` 取上屏文字，所以回调里改写候选的 `text` 就能换掉上屏内容。改的是 `get_genuine()`：`uniquifier` 等包装器的 `text` 为空时取被包装的候选，而 `set_text` 只对 `SimpleCandidate` 生效。选重键、空格、鼠标点选最后都走 `Context::Commit()`，所以都会展开。

**正文每行不超过 16 个全宽字符**（汉字、全角标点算 1，ASCII 字母数字和空格算半个）。数值一行两项是按七八位数估过的。以后往报告里加项时也要守住这个宽度；开头三行、两行分布和末尾两行不受限制。

`tjs` 列出所选时段中最长的那个（不带时段字母时即累计）里有数据的安装。报告只看当前方案。不单独做导出：Rime 同步时会把整个库导出为同步目录下的 `snow_statistics.userdb.txt`，包含全部方案、全部安装的逐日原始计数。

### 已知局限

- 缓冲模式下的顶屏只 confirm 不上屏，移交量不起作用；缓冲区整体上屏时，按键都算在那一次上。
- 移交假设推回的编码里每个 $e_i=+1$ 的键都往输入框里加了一个字符。推回的那段里如果有不进 `input` 的键，分界会偏，上一次上屏多记几码，下一次少记；删掉推回的编码时下一次的 $m_j$ 还可能不是正数，被整次丢掉。
- 极速窗口不跨会话：切换方案或重启输入法时，没满一分钟的窗口会被丢掉；跨零点的窗口记在结算那天。报告里极速和均速取最大值，不会因此低于均速，但丢掉的那段如果比均速和所有窗口都快，也找不回来。
- 并击状态是镜像的。如果和 C++ 不同步，嵌套的 `process_key` 可能返回 false，这时外层仍返回 `kAccepted`：返回 `kRejected` 会让 `unhandled_key_notifier` 触发第二次，代价只是这次松开不会再交给应用。
- 辅助码并击（`v…v`）和它所属的音节是两组并击，但 `back_syllable` 未必按这个粒度删，退格后的有效按键会有偏差。

### 验证方法

spec 里**没有**统计的用例（mira 的按键都是瞬间完成的，时长和速度没有意义，报告格式又常改）。改动统计逻辑后，用临时用例混合各种上屏方式，再检查第二部分的两个不变式。临时用例直接用 mira 跑（`scripts/test.ts` 跑完会删掉临时目录）。mira 的数据目录是 `$TMPDIR/mira/data/`，**每个 deploy 都会重建**，所以临时用例只写一个 deploy。跑完后在数据目录里用 `rime_dict_manager -b` 把库导出成同步快照，逐个单元检查：

```sh
cd "$TMPDIR/mira/data" && rime_dict_manager -b snow_statistics >/dev/null
cat sync/*/snow_statistics.userdb.txt | python3 -c '
import re, sys, collections
rows = collections.defaultdict(dict)
for line in sys.stdin:
    if line.startswith("#"):
        continue
    key, field, value = line.rstrip("\n").split("\t")
    rows[key][field] = int(re.match(r"c=(-?\d+)", value).group(1))
for key, r in rows.items():
    f = lambda kind, w: sum(w(int(k[len(kind):])) * v for k, v in r.items() if re.fullmatch(kind + r"\d+", k))
    assert f("word", lambda i: 1) == f("code", lambda i: 1), (key, r)
    assert f("code", lambda i: i) <= r.get("keys", 0), (key, r)
'
```

要追踪每个键、每次结算，就临时在 `processor.func` / `record` 里用 `io.open(..., "a")` 写一个文件。`log.error` 和 stderr 在 mira 的输出里都看不到。
